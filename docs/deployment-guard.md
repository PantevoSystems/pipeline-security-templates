# Deployment Guard Integration

[Deployment Guard](https://www.pantevosystems.com/deployment-guard) by Pantevo Systems provides deterministic deployment risk scoring (0–100, with AI-generated explanations) on top of your existing security pipeline. It analyzes diff complexity, Kubernetes changes, dependency risk, and incident history to give you a single actionable score before every deployment.

## Quick start

Add it to your existing security pipeline by using the `full-stack-with-guard.yml` workflow:

~~~yaml
jobs:
  security:
    uses: PantevoSystems/pipeline-security-templates/.github/workflows/full-stack-with-guard.yml@v1.2.4
    permissions:
      contents: read
      security-events: write
      actions: read
    secrets:
      guard-api-key: ${{ secrets.GUARD_API_KEY }}
~~~

## Get an API key

1. Sign up at [pantevosystems.com/signup](https://www.pantevosystems.com/signup) — free tier, no credit card required.
2. Copy your API key from the dashboard.
3. Add it as a GitHub repository secret named `GUARD_API_KEY`:
   - Repository Settings → Secrets and variables → Actions → New repository secret

## Inputs (Deployment Guard)

| Input | Default | Effect |
|---|---|---|
| `guard-fail-on-warn` | `false` | Also fail on WARN (BLOCKED always fails) |
| `guard-fail-open` | `true` | API unreachable, HTTP 429/5xx or an invalid response only warn and the pipeline continues (advisory gate). `false`: the guard job fails (**fail-closed**). Invalid API key (401/403) and rejected requests (400/422) always fail. |
| `allow-missing-key` | `false` | `true`: only warn and skip when the `guard-api-key` secret is missing. Default: the guard job fails. |
| `skip-guard` | `false` | Don't run the guard job at all |

Further behaviour:

- **Scanner results are verified.** If a scanner job that was not skipped ends with `failure` or `cancelled`, the guard job fails with *"scanner did not complete, refusing to score with 0 findings"* instead of reporting PASS with zero findings. (With `fail-on-issues: true` a scanner also fails when it finds issues — then the pipeline is red anyway.)
- **Full history.** The guard checks out with `fetch-depth: 0` and diffs against the push's `before` commit, the pull request's base commit or `HEAD~1`. A missing base commit fails the job.
- **Pinning.** Third-party actions are pinned to commit SHAs; the Deployment Guard action itself is referenced as `@v1`. Reference this workflow by release tag (`@v1.2.4`) or commit SHA, never `@main`.

## What data is sent

The guard step sends one JSON request per run to the Deployment Guard API containing:

- repository name, branch name and commit SHA
- the **paths** of changed files (max. 500, each max. 300 characters) — **no file contents**
- line and file counts of the diff
- Kubernetes/Helm flags (changed manifests, single replica, missing PDB, Helm values changed, chart bumped)
- dependency changes and major version bump counts
- scanner finding counts (Trivy CRITICAL/HIGH, Semgrep total/high, Checkov failed/critical)
- incident counts (if passed)
- repo type indicators (Dockerfile, Python/Node deps, Terraform, `setup.py`: yes/no)

Not sent: source code, diff contents, file contents, commit messages. The score itself is a deterministic formula; the explanation text is generated by OpenAI from the computed factors and the changed file paths.

The GitLab and Bitbucket guard templates send less: repository, branch, commit SHA and line/file counts (the backend download templates additionally send K8s/Helm counts derived from file names) — no file paths.

## How it works

Deployment Guard analyzes up to **five adaptively weighted factors**:

- **Diff complexity** — lines and files changed, scaled logarithmically
- **Kubernetes risk** — manifest changes, Helm value bumps, ArgoCD sync status, single replica, missing PodDisruptionBudget
- **Dependency risk** — count of dependency updates and major version bumps
- **Incident history** — production incidents in the last 7 and 30 days
- **Pipeline findings** *(optional)* — CRITICAL/HIGH CVEs from Trivy, SAST findings from Semgrep, IaC failures from Checkov — automatically forwarded when using `full-stack-with-guard.yml`

The weighting is **adaptive** — repos without Kubernetes context or without pipeline scanners get the weights automatically redistributed. A frontend repo without K8s gets evaluated just as fairly as a full-stack backend with Helm and security scans.

**Repo history as context:** On every analysis, the current score is matched against the median and trend of recent analyses for the same repository. If the score is significantly above the repo's median, it nudges up (max +5 points). If it fits the usual pattern, it can soften by a few points (max -3). Active after 5 historical analyses — Deployment Guard implicitly learns what's "normal" for your repo.

The factors combine into a single 0–100 score with a verdict:

| Score | Verdict | Status |
|---|---|---|
| 0–49 | LOW RISK | ✅ PASS |
| 50–74 | MEDIUM RISK | ⚠️ WARN |
| 75–84 | HIGH RISK | ❌ BLOCKED |
| 85–100 | CRITICAL RISK | ❌ BLOCKED |

Thresholds (defaults: WARN at 50, BLOCK at 75) are configurable in the dashboard for Team plan users.

## Combining with security scans

Deployment Guard works best layered on top of detailed security findings. The `full-stack-with-guard.yml` workflow runs Trivy, Semgrep, Checkov, and Deployment Guard together — detailed findings land in the GitHub Security tab while the risk score acts as a final gate. **Findings counts flow directly into the risk score** (15% weighting when present).

~~~yaml
jobs:
  security:
    uses: PantevoSystems/pipeline-security-templates/.github/workflows/full-stack-with-guard.yml@v1.2.4
    permissions:
      contents: read
      security-events: write
      actions: read
    with:
      trivy-severity: 'CRITICAL,HIGH'
      semgrep-config: 'p/default'
      checkov-framework: 'all'
      guard-fail-on-warn: false
      guard-fail-open: true       # default: API outages only warn; false = fail closed
      allow-missing-key: false    # default: a missing secret fails the guard job
      fail-on-issues: false
    secrets:
      guard-api-key: ${{ secrets.GUARD_API_KEY }}
~~~
